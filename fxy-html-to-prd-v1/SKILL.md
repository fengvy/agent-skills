# Prototype To Prd（原型反推 PRD）

## Overview

把已有产品原型（HTML）反向推导为**项目级**、结构化、可交付的 PRD：一个项目一份 PRD，覆盖全部端；新端按端增量追加，不拆成多份 PRD。跨端关系统一写第六章，不另建台账。全文按【已确认】/【推断】/【待确认】三级标注来源，面向研发、设计、业务多方阅读，语言简洁专业、避免口语化。撰写约束见「撰写铁律」，产出长度上限见「篇幅纪律」。

**读者与产出**：读者是研发（含跨端集成方）、设计、业务与后续接手的人。产出一份项目级 PRD，写产品业务层面与跨端契约，用于确认口径与指导实现；机器级类型、正则、幂等、错误码等实现细节不在本 PRD 展开。

## 输入与前置检查

1. **确认原型来源**：
   - 本地文件路径 → 直接读取；粘贴代码 → 直接解析；
   - 线上链接（资料库 / 团队空间 hosted 原型）→ 先用 curl/WebFetch 拉线上当前版本再解析。**不要信任本地副本或历史版本**，防止以旧版本反推。
2. **缺材料就问**：消息中未含文件 / 路径 / 链接时，不臆造原型内容，先向用户索取输入材料。
3. **确认项目与端**：先判断是一个项目还是多个独立项目；一个项目默认一份 PRD。列出端清单、每端对应的原型材料、本次要生成/更新哪一端。若已有 `<项目名>-PRD.md`，先读取并追加，不重写已覆盖端。
4. **确认覆盖范围**：全项目所有端还是指定端。材料齐全时默认覆盖全部已提供端；只有部分端时，未提供端的跨端契约标【待确认】+ 责任端，**不得代写对方端行为**。
5. **确认自足度**：问清本 PRD 的业务口径是否足以让研发确认。凡无法从原型判定的，必须写入第九章并给出建议方案或决策建议，不得留白。
6. **确认业务目标与成功指标（可选）**：原型通常不体现业务目标。用户能提供时写入第二章并标明来源；未提供时第二章写「【待确认】原型未体现业务目标与成功指标」并进第九章，**不得编造数值或指标**。

## 项目级与多端处理

多端项目的默认工作方式不是「每端一份 PRD」，而是「一个项目一份 PRD + 按端增量追加」：

- PRD 第五章以端分节：一个端一个 `#### 5.X <端名>` 分节，模块挂在分节下；模块编号全项目连续，不按端重置；端名在全文逐字一致。
- 跨端交互只写第六章「跨端契约表」；第五章只写本端行为并引用契约 ID。
- **首次生成**：建立项目骨架（端清单、页面、角色、术语、契约骨架），先写已有端的页面与模块；未提供端不编造。
- **每次新增一端**：读取现有 PRD，只追加该端页面与模块，更新第六章契约、共享角色/术语/枚举，**不重写已有端**。
- **每轮结束做跨端对账**：每个契约至少一侧有描述，未知侧有责任端；共享结果枚举/状态名/字段名一致；同一共享对象只有一个落库方。
- **不新增跨端台账或其他文档**：PRD 本身就是跨端上下文。

## 反推方法

### Step 1 通读与结构识别

识别端、页面、模块：多端项目先按原型文件 / 路由 / 导航区分端，再识别各端页面数量、入口与所属模块（导航菜单、sidebar、tab、面包屑是模块边界的主要线索）。HTML 体积大时，先用 `scripts/extract_prototype_ui.py` 提取索引，再回源码通读关键片段；**若提取出的文本极少，改用 `scripts/dump_prototype_js.py`**（JS 渲染型原型，见 Scripts 节）——从 `NAV` / `TITLES` / `render` 路由这类常量与分发函数切入定位模块边界最快。

### Step 2 逐端、逐模块采集

逐端、逐模块收集界面可见证据：标题与说明文案、表单 label、表格列头（th）、按钮、下拉选项、弹窗、状态标签、空态/错误态文案；以及元素属性——必填标识、placeholder、禁用态、maxlength、枚举选项。不同端的同名页面不要合并；端与端的边界写进第六章。

### Step 3 逻辑反推（只从证据出发）

从界面痕迹反推五类逻辑，**证据不足一律进【待确认】，不编造**：页面跳转（onclick / href / 路由）、操作流程链（入口→操作→反馈→结果）、状态流转（按钮文案与状态标签）、校验规则（占位符 / 提示文案 / 必填星号 / maxlength）、跨端交互（接口调用、共享数据对象、角色交接、异步状态、失败/拒绝提示）。跨端交互只能确认本端行为时，只写本端一侧；对方端行为进【待确认】并写责任端。

### Step 4 标注分级（全文唯一判定标准）

| 标注    | 含义               | 使用要求                                      |
| ----- | ---------------- | ----------------------------------------- |
| 【已确认】 | 直接见于原型 UI 文本/交互  | 直接描述，来源即界面                                |
| 【推断】  | 原型隐含但未明示         | **必须写明依据**（如"由按钮文案 X 推断存在状态 Y"）           |
| 【待确认】 | 原型无法判定           | 写入第九章：问题描述、影响端/模块/字段、建议方案、责任端、优先级               |

## 撰写铁律

1. **不臆造**：所有推断带依据；无法确定的进待确认清单，不得默认成文。业务目标与成功指标同理：无原型证据且用户未提供时，标【待确认】，不编数值。跨端信息同理：对方端未提供原型时，只写本端行为，对方侧标【待确认】并写责任端。
2. **配置驱动的表单字段不逐条固化**（字段规则的唯一例外）：由后台配置下发、前端动态渲染的字段（如 CRF 表单字段、样本采集字段，字段/分组/值集/必填/参考范围均可配置）不进字段清单表，改写「字段来源与渲染/录入口径」——①字段来源（哪个系统/字典配置，原型内联字典仅为模拟）；②前端统一渲染与校验口径（控件映射、必填标识、条目组增删行、参考范围展示）；③提交产出的数据结构字段（如需研发对齐）。文中须声明"字段清单以配置为准，本 PRD 不逐条固化"。
   **判断标准**：字段是"配置数据"还是"H5 自有数据对象/交互表单"——后者（待办卡结构、通知对象、批次对象、只读展示字段等）仍照常列全。
3. **跨系统引用字段收口**：仅当 ① 字段在页面实际展示（列表/详情/只读引用），或 ② 字段参与本模块业务逻辑（校验、流程分支、状态判定），才列入字段定义/数据依赖。仅在系统间内部传递的字段不添加；跨系统数据边界写清 `读什么 / 写什么 / 由哪个系统提供 / 本系统是否落库`，不写接口技术细节。
4. **模块编号**：统一 M01、M02…，**全项目连续，不按端重置**；模块挂在对应端分节下，全文引用一致。不与原型页面一一对应时可拆分/归并，但需说明划分逻辑。
5. **字段完整性**：字段表不遗漏原型中任何可见数据项（展示/输入/隐藏都要入表）；枚举列出全部可选值及含义；金额标单位与精度；时间标格式（如 YYYY-MM-DD HH:mm:ss）；从 UI 文本反推的字段标"推断自界面"。
6. **状态流转**：仅在涉及有状态对象（订单、审批、任务等）时填写；不涉及则整节省略（见篇幅纪律 3），更不编造。
7. **异常与降级**：必须给出明确业务决策（阻断操作 / 降级展示 / 提示并给出具体文案），不要只写"提示用户"。
8. **区分「已接线」与「未接线」，且必须双向核验**：原型中定义但从未被调用的函数、变量、配置项属于**死代码或未接线功能**，不得写成已实现的正向功能；应作为「原型未实现项」列入待确认清单，或在模块内显式标注未生效。
   **两个方向都要查，且反向错误更严重**：
   - **正向（查漏写）**：原型里有、文档没写 → 实施方不知道有这功能，可能漏做（*消极错误*）
   - **反向（查误判）**：「未实现 / 未接线 / 死代码 / 演示态」这类声明本身可能是错的 → 实施方被明确告知"不用做"，会**主动跳过**一个真实存在的功能（*积极错误*）

   **反向核验必须按维度分查，不能只数「引用」**：「未实现」在中文里是好几件不同的事 ——
   | 声明写法 | 实际含义 | 该查的维度 |
   | --- | --- | --- |
   | 恒为空 / 不回写 / 未赋值 | 从不**写入** | 赋值次数 |
   | 未接线 / 无入口 / 未调用 | 从不**被调用** | 调用次数 |
   | 在 X 处未生效 / 渲染时未使用 | **特定位置**不生效 | 无法自动判定，须人工读 |
   | 未实现 / 不存在 | 从未出现 | 任何使用 |

   曾经的真实教训：`roleMenuSel` 被读取 2 次（引用>0），但**从未被赋值**，因此「按角色隐藏菜单未生效」的声明完全正确 —— 只数引用就会把它误判成"已实现"。同理，只用 `name()` 查调用会漏掉带参形态，把 `name(a,b)` 这种真实调用误判为死代码。
   **用 `scripts/audit_unimplemented.py` 跑反向核验**（见 Scripts 节），不要凭印象下结论。
9. **未生效的「演示态」必须标注**：原型中通过 toast 占位、无事件绑定的筛选控件、保存不回写的配置弹窗等，均属演示态。写入 PRD 时按「功能描述 + 明确标注未实现」处理，不可描述为可用功能。
10. **项目级单文档**：多端项目默认一份 PRD，端只做章节分组，不拆成多份 PRD，不另建跨端台账；跨端契约只写第六章。已有 PRD 时增量追加，不重写已覆盖端。

## 反例对照（最常出错的三种写法）

这三组是本 skill 历史产出里最常犯的错。**写作时对照这三组看一眼，比记住上面 10 条抽象铁律更有效。**

```diff
# ✗ 臆造：原型里没有的东西被写成了功能
- 模块支持批量导入受试者，系统会自动校验重复并给出提示。

# ✓ 带依据的推断 + 未体现项入清单
- 【推断】支持批量导入。依据：列表页存在「批量导入」按钮与文件选择控件，但导入结果提示文案在原型中未体现。
- 【待确认】判重字段（按哪个字段判重复）、命中后是覆盖还是跳过 —— 原型中未体现。
```

```diff
# ✗ 异常策略模糊：读者读完还是不知道该怎么做
- 数据加载失败时提示用户。
- 视情况允许用户继续操作。

# ✓ 明确业务决策（阻断 / 降级 / 提示）+ 具体文案原文
- 加载失败：阻断操作，页面展示「数据加载失败，请重试」+ 重试按钮；重试仍失败则保留上次成功数据（降级展示）。
- 发布时项目已锁库：阻断，toast「项目已锁库/关闭，方案只读，不允许发布」。
```

```diff
# ✗ 复述型冗长：换了说法把同一件事说三遍，篇幅涨了、信息没涨
- 第五章 M01 字段表列了「方案状态」的全部属性
- 第七章全局字段总表又完整列一遍「方案状态」的全部属性
- 第六章依赖矩阵里再说明一次「方案状态会影响什么」

# ✓ 每处只写一次：定义在模块内、第七章只做索引、依赖只在第六章
- 第五章 M01 字段表： 方案状态 | 枚举 | 草稿 / 已发布 | 本系统
- 第七章索引： 方案状态 | 方案状态 | M01、M02
- 第六章： M02 方案详情 → M03 临床访视计划 | 发布时按访视配置展开受试者任务实例
```

## 篇幅纪律（硬约束）

历史产出偏冗长。以下为强制约束，交付前逐条对照：

1. **同一规则全文只写一次**，不换说法重复。具体：字段属性只在第五章模块内定义，第七章只做索引；模块间依赖与跨端交互只在第六章表达，第五章不列"本模块影响范围"，跨端调用只引用契约 ID。
2. **第五章按模块复杂度分级**：
   - **A 类（复杂模块）**——有状态机、多分支流程、跨模块数据依赖：按 5 项适用内容展开；
   - **B 类（简单模块）**——纯展示 / 单步操作 / 无状态流转：只写第 1、2、5 项；有失败路径时补第 4 项；其余省略；
   - 每个模块开头用一句话标注 A/B 类及判定理由。
   - **超出篇幅时先拆分，不要硬压**：若单个 A 类模块本身承载多个能力（原型一个页面里有多个 tab / 内联面板 / 二级页），应按能力拆成子模块（M02a / M02b…）分别成节，而不是把内容压掉或塞进一节。**判断依据是内容是否真的是新增信息**——若超出源自复述，删复述；若源自信息密度高，拆分。
3. **空项直接省略**：不适用的小节不要出现，不写"不适用""无""暂无"。
4. **第八章非功能需求**：原型无证据支撑的项直接不写，不要为凑栏目硬编指标。
5. **单模块篇幅参考**：A 类约 1 屏内（不含字段表），B 类约半屏。该值是参考而非硬上限——超出时按第 2 条判断该拆还是该删，并在交付说明中给出实际篇幅与预估的差异。
6. **项目级可扫读**：按端分节；文首给每端最短阅读路径；研发只需读本端分节 + 第三章本端行 + 第六章契约，不要求通读全文。

## 读者与写作要求

本 PRD 的实际读者有五类，他们读完要做的事不同 —— 写作要求由读者反推，而不是凭「写得好」的感觉。

| 读者 | 读完要能做什么 |
| --- | --- |
| 本端研发 | 据此实现，不必再回来问「点这个按钮会发生什么」 |
| 跨端集成方 | 据第六章契约完成对接，知道双方职责、输入输出、失败反馈与责任端 |
| 设计 | 据此刻画与核对交互，能发现与现有设计体系的冲突 |
| 业务 / 产品 | 据此确认口径，能指出「我们不是这么做的」 |
| 后续接手的人或 AI | 不打开原型就能理解系统全貌，并能按标注定位回原型验证 |

由此得到 5 条可验证的写作要求（不是风格建议，是验收条件）：

1. **功能可定位**：每个功能点都挂在具体模块编号下，并能指出所属端、页面 / 路由。
2. **结论可回溯**：每条结论带来源标注（界面文案原文 / 函数或控件名 / 【推断】依据）。读者质疑时能查证，不必重读原型。
3. **交互可复现**：状态、触发条件、边界、提示文案齐全；**全文不出现「视情况」「一般会」「可能」「应该」**。
4. **未知不埋雷**：无法判定的全部进第九章并标责任端与优先级，不在正文里含糊带过。
5. **术语唯一**：同一对象全文一个名字（不要一处叫「访视」一处叫「采集点」）；同一底层数据在不同模块或不同端显示为不同名称时，必须显式写出映射关系。

## 输出结构

撰写前依次读取两个文件：

| 文件 | 用途 | 服务对象 |
| --- | --- | --- |
| `references/prd-output-template.md` | 项目级 PRD 九章骨架与各章要求，**以它为准** | 人 |
| `references/example-module.md` | PRD 的 A 类 / B 类模块示例，锚定颗粒度与标注方式 | 写作者 |

**产出**：

- **一个项目一份 PRD**：`<项目名>-PRD.md`，覆盖全部端；多端按端增量追加，不重写已覆盖端。
- 模块编号（M01…）全项目连续，不按端重置。

**多端项目跑对账脚本时加 `--section <端名>`**：脚本只保留第五章该端分节（含可选的「共用」分节），第三、六、七、九章表格只保留该端行；不要直接拿全项目 PRD 跑，否则其他端的同名按钮/标识符会造成假覆盖或假一致。端名必须与第五章分节标题逐字一致，对不上会报错并列出既有分节。

**篇幅与颗粒度上的临场判断，优先以示例为准，而不是凭感觉决定写多细。** 示例只锚定结构、颗粒度与标注方式，其业务内容不要照搬。

## Scripts

四个脚本均为 stdlib-only，无依赖。

### scripts/extract_prototype_ui.py —— 静态文本型原型

从原型 HTML 提取可见文本与交互元素索引，辅助识别模块与字段。

```bash
python3 scripts/extract_prototype_ui.py <原型.html> [--no-dedupe] [--plain-only]
```

完整用法与输出图例见脚本内 docstring。

### scripts/dump_prototype_js.py —— JS 渲染型原型（重要）

**若上一个脚本只提取出十几行文本，说明该原型是 JS 渲染的**——模块与字段全在内联脚本和 mock 数据里，静态 HTML 抓不到。此时改用本脚本：

```bash
python3 scripts/dump_prototype_js.py list                 # 列出全部函数及体量（定位视图入口最快的方式）
python3 scripts/dump_prototype_js.py fn <函数名> [...]     # 抽函数体（按花括号配对，折行输出）
python3 scripts/dump_prototype_js.py var <变量名> [...]    # 抽 "var X =" 赋值块（mock 数据在这里）
python3 scripts/dump_prototype_js.py lines <起> <止>       # 抽原始行区间
```

可加 `--file`（省略时自动取当前目录下唯一的 `.html`，多文件须显式指定）、`--width`（折行宽度，默认 180）、`--grep`（过滤输出）。
**原型单行常达 2000+ 字符，直接 Read 会被截断，必须用本脚本取函数体。** 先 `list` 看体量最大的视图函数，通常数量级最高的就是主工作台。

### scripts/audit_coverage.py —— 交付前查功能点遗漏

把原型里**所有可点击入口的可见文案**抽出来，逐个检查是否出现在写好的 PRD 里，输出未覆盖清单。

```bash
python3 scripts/audit_coverage.py <原型.html> <PRD.md> [--section 端名] [--show-covered]
```

原型里每个 `onclick` 都是一个功能入口。**未覆盖项要逐条判定**：是真遗漏（行为没写），还是仅未引按钮原文（行为写了但没引按钮文案）。判定时用处理器函数名回查实现：
```bash
python3 scripts/dump_prototype_js.py fn <未覆盖项的处理器名>
```
**这一步是「功能点有没有遗漏」的唯一硬证据**，不跑就下"无遗漏"的结论属于凭印象。

### scripts/audit_unimplemented.py —— 反向核验「未实现」类声明

覆盖率对账只查「原型有 → 文档没写」。反方向同样要查：文档声称「未实现 / 未接线 / 死代码 / 占位 / 不生效」时，**这个声明本身可能是错的**。

```bash
python3 scripts/audit_unimplemented.py <原型.html> <PRD.md> [--section 端名] [--show-ok] [--claims-only]
```

从文档抽出「未实现类」声明 → 提取其中 `反引号标识符` → 回原型**按维度**计数（定义 / 赋值 / 调用 / 读取）→ 给三态判定：

| 判定 | 含义 |
| --- | --- |
| ✓ 一致 | 关注维度计数为 0，证据支持声明 |
| ⚠ 不一致 | 关注维度有计数，且声明是全局性的 → 需回源码确认 |
| ？ 须人工判断 | 声明含位置限定词（"在…处/时"）、未指名标识符、或标识符过短（名字冲突风险） |

**⚠ 不等于声明错误**（可能是定义了但走不到的分支），**？ 更不等于有问题** —— 都须回源码确认后再改结论。脚本只摆证据，不下结论。

**脚本只能提速，不能替代判断**——弹窗内容、onclick 跳转、死代码甄别仍须回源码交叉验证。
